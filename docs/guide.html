1. What is a CLOB?

A Central Limit Order Book (CLOB) is the core data structure of most equity and crypto exchanges. It holds all resting (passive) buy and sell orders for one instrument, sorted so the matching engine always knows who to trade with next.

Bids (buyers)

100× 15
99× 30
98× 40

Asks (sellers)

100× 20
101× 50
102× 10
Sorting rules
  • Bids — highest price first (best bid at top)
  • Asks — lowest price first (best ask at top)
  • Spread — gap between best bid and best ask (here: 100 vs 100 → zero spread, locked market)

Price–time priority

When an aggressive order arrives, the engine matches using two rules:

  1. Price priority — take the best price on the opposite side first
  2. Time priority — at the same price, the oldest order fills first (FIFO queue)

2. The matching loop

In OrderBook.matchAggressive(), an incoming taker order walks the opposite side of the book until it is fully filled or can no longer cross the limit price.

Incoming order → Crosses best price? → Fill FIFO at level → More qty left? → Rest or cancel remainder 
// Simplified matching logic (OrderBook.java)
while (remaining > 0 && opposite side has liquidity) {
    bestPrice = opposite.firstEntry()
    if (!priceCrosses(takerLimit, bestPrice)) break

    while (remaining > 0 && level not empty) {
        maker = level.peekFirst()          // oldest at this price
        fillQty = min(remaining, maker.qty)
        emit trade
        update or remove maker
    }
}
return remaining

See §2b Matching data structures for TreeMap vs array/pool diagrams.

Example: limit buy crosses the ask

Book: asks at 100×20 and 101×50. Submit BUY 25 @ 100:

1Fill 20 from ask @ 100 (oldest maker)5
2Limit 100 cannot cross ask @ 101 → stop5
3Rest 5 as bid @ 100 (limit order behavior)0 resting logic

2b. Matching data structures

The matching rules are the same everywhere — price-time priority, FIFO within a level. What changes is the containers underneath: how you find the best price, store orders, and update the book without allocating on the hot path.

Both implementations expose the same API via OrderBookView. MatchingEngine calls matchAggressive() first, then optionally addRestingOrder() for limit remainders.

Three layers

Layer 1 — Price levels

Question: “What prices exist, and which is best?”

Tree book: two TreeMaps (sorted). Fast book: two FastLevel[] arrays indexed by tick + cached best bid/ask.

Layer 2 — Orders at a level

Question: “Who’s first in line at this price?”

Tree book: ArrayDeque<Order> FIFO. Fast book: intrusive doubly-linked list of pooled nodes.

Layer 3 — Order index

Question: “Given orderId, how do I cancel?”

Tree: orderId → (side, price) then scan deque. Fast: orderId → pool slot then O(1) unlink.

3. Limit orders

A limit order says: “Buy/sell up to qty units, but only at this price or better.” Unfilled quantity rests on the book as passive liquidity.

Limit order

Rests unfilled quantity stays on book

Price protection won't pay more (buy) or sell cheaper (sell) than limit

API: submitLimitOrder(id, side, priceTicks, qty)

engine.submitLimitOrder(5, Side.BUY, 100, 25);
// MatchResult: trades=[...], remainingQuantity=5, resting=true

4. Market orders

A market order says: “Fill me now at whatever prices are available.” It has no price cap (in this toy engine: Long.MAX_VALUE for buys, Long.MIN_VALUE for sells).

Market order

Never rests unfilled qty is discarded

No price limit walks through multiple price levels

Immediate takes all available liquidity aggressively

API: submitMarketOrder(id, side, qty)

Example

Asks: 100×15, 101×40. MARKET BUY 30:

TradePriceQty
110015
210115

Book after: ask 101×25 remaining. No bid added — market orders never rest.

engine.submitMarketOrder(3, Side.BUY, 30);
// MatchResult: orderType=MARKET, resting=false

5. IOC — Immediate or Cancel

An IOC (Immediate-or-Cancel) order combines limit price protection with market-like urgency: match everything you can right now at your limit price, then cancel any unfilled remainder. It never rests on the book.

IOC order

Price limit like a limit order

Never rests leftover qty cancelled immediately

Partial fill OK common in institutional flow

API: submitIocOrder(id, side, priceTicks, qty)

Limit vs Market vs IOC

Limit

Price limit ✓
Rests ✓
Use: provide liquidity

Market

Price limit ✗
Rests ✗
Use: urgency, pay the spread

IOC

Price limit ✓
Rests ✗
Use: take liquidity without leaving an order

Example

Ask: 100×10 only. IOC BUY 25 @ 100 → fill 10, cancel remaining 15.

engine.submitIocOrder(2, Side.BUY, 100, 25);
// trades: 1 fill of 10, remainingQuantity=15, resting=false

6. FOK — Fill or Kill

A FOK (Fill-or-Kill) order is all-or-nothing: it must fill the entire quantity at your limit price (or better) immediately, or the whole order is rejected with zero trades. No partial fills. Nothing rests on the book.

FOK vs IOC

IOC — partial fill OK, cancel remainder

FOK — full fill required, otherwise reject everything

API: submitFokOrder(id, side, priceTicks, qty)

How clob-lab implements it

// 1. Check available liquidity WITHOUT mutating the book
if (book.availableAtOrBetter(side, limitPrice) < quantity)
    return rejected;

// 2. Only then match aggressively
return submit(..., allowRest=false, OrderType.FOK);

Example

Ask: 100×10 only. FOK BUY 25 @ 100 → rejected, book unchanged.

Same book. FOK BUY 10 @ 100 → fills all 10, book ask side empty at 100.

8. Event journal & replay

Production exchanges don't just mutate state — they append every input to a journal. That gives you audit trails, crash recovery, and deterministic replay for testing.

Why journal?
  • Audit — reconstruct exactly what happened and when
  • Recovery — rebuild book state after a crash from the log
  • Testing — replay production events in a dev engine
  • Determinism — same events → same final book (if matching is deterministic)

How clob-lab does it

MatchingEngine.Journaled live = new MatchingEngine.Journaled();

live.submitLimitOrder(1, Side.SELL, 100, 30);
live.submitLimitOrder(2, Side.BUY,  100, 10);
live.submitIocOrder(3, Side.BUY, 99, 5);
live.cancel(1);

// Rebuild a fresh engine from the log
MatchingEngine replayed = live.replay();
// replayed.book() should equal live.book()

Each journal entry is an OrderEvent:

FieldMeaning
eventIdMonotonic sequence in the journal
kindSUBMIT or CANCEL
orderTypeLIMIT, MARKET, IOC, or FOK
orderId, side, priceTicks, quantityOrder details (price null for market)

EventReplayer.replay() creates a new MatchingEngine and applies events in order — no double-journaling on replay.

11. Load testing

Load tests differ from microbenchmarks: they run a realistic mix of operations continuously for many seconds and report throughput (ops/sec) plus latency percentiles under sustained traffic. 

./gradlew runLoadTest
./gradlew runLoadTest --args="--mode=multi --threads=8 --duration=30"

Modes

ModeWhat it measures
singleOne thread, one book — peak hot-path throughput
multiN threads, N independent books — aggregate multi-symbol throughput
contendedN threads, one shared book (synchronized) — lock contention stress

Mode comparison (8 threads, 10s duration, sample run)

These numbers illustrate why mode matters. Throughput and tail latency vary by orders of magnitude — not because the matcher got slower, but because the threading model changed.

Mode Threads Throughput p50 latency p99 latency Interpretation
single 1 ~13k ops/sec ~80 ns spiky (GC) One symbol, mixed workload — realistic per-shard ceiling
multi 8 ~7.7M ops/sec ~200 ns ~1.8 µs Production pattern: one book per thread (sharded symbols)
contended 8 ~22k ops/sec ~80 ns ~16 ms Anti-pattern: all threads fight one synchronized lock
Why contended looks “much slower”

In contended mode, eight threads serialize on a single shared MatchingEngine. p50 can still look fast (~80 ns) when a thread briefly wins the lock, but p99 explodes to milliseconds from lock queueing and OS scheduling — not from match logic (~30 ns in JMH).

Compare against ./gradlew run (~125 ns p50) or ./gradlew jmh (~27 ns/op) for isolated hot-path speed. Use multi for aggregate exchange throughput.

Default traffic mix (per 100 ops)

  • 65% limit submit
  • 20% cancel
  • 10% IOC
  • 5% L2 snapshot

Sample output

Throughput: 245,100 ops/sec
Latency: min=120ns p50=842ns p99=4102ns p999=12000ns max=85000ns

13a. The ring buffer — what it does

The ring is a queue between routing and matching — one per symbol shard. It holds SequencedCommand objects (order + cancel + global sequence) until the matcher consumes them. Inspired by LMAX Disruptor / Chronicle: pre-allocated slots, single-producer single-consumer (SPSC), no alloc on offer/poll.

One sentence

The ring buffers sequenced orders per symbol so ingress can push fast, the matcher consumes at its own pace, and the book never sees concurrent writers.

Where it runs (and where it doesn't)

Entry pointUses ring?Path
./gradlew runPipelineYesCloudExchange → SymbolShard.inboundRing
./gradlew runDemoNoMain → MatchingEngine directly
./gradlew runLoadTestNoLoadTestRunner → engine directly
./gradlew run / jmhNoBenchmarks bypass pipeline

Created in SymbolShard when you build CloudExchange(symbolCount, ringCapacity, …). Each symbol gets its own RingBuffer<SequencedCommand> (default demo: capacity 1024).

What problem it solves

  • Decouple — ingress accepts orders while the matcher works (in production: different threads)
  • Buffer bursts — absorb microsecond spikes instead of blocking the gateway
  • Single consumer — matcher sees one ordered stream per symbol
  • Back-pressure — offer() returns false when full. flushBatch keeps leftovers in ingress and reports ExchangeTick.deferred(); next flush retries. submit() itself always succeeds (unbounded ingress list).

Flow through the pipeline

submit() → ingressBatch (ArrayList — not the ring yet)
flushBatch() → Sequencer + FancyPQ reorder
router.route() → inboundRing.offer(command) — producer writes ring
shard.processAll() → inboundRing.poll() → MatchingEngine — consumer drains ring
FairMarketDataPublisher.flush() + journal

13b. Industry vs clob-lab

clob-lab uses the right blueprint at teaching scale: one book per instrument, sharded matchers, pipeline stages, journal, market-data fanout. It is not a production exchange — but the mental model matches what equities, crypto spot, and most CLOB venues actually build.

One ticker = one order book

Real exchanges never mix AAPL and GOOG in a single book. Orders only match within the same instrument. 10,000 tickers → 10,000 independent matchers (logically; physically they may share machines).

Java vs C++ in trading

C++

Manual memory, no GC pauses, used for matching engines, gateways, and FPGA-adjacent paths when nanoseconds count.

Java

Common for buy-side, risk, and many exchange middle tiers. With disciplined coding (pools, off-heap, Disruptor ring buffers), microsecond latency is achievable.

16. Learn from the codebase

This repo is small enough to read end-to-end, but it has two layers. Start with matching rules, then add the pipeline. Do not start in FastOrderBook or CloudExchange — those hide the rules behind performance and orchestration.

How to use this section

Walk the steps in order. After each step, run the command, then open the listed files. The refactor list at the bottom is homework — bugs and cleanups that teach more than reading.

Read order (the map)

model/ → OrderBook (TREE) → MatchingEngine → tests + demo → FastOrderBook → pipeline

Step-by-step walkthrough

1

Domain types — 10 minutes

Open model/Side.java, Order.java, OrderType.java, Trade.java, MatchResult.java.

Notice: prices are long ticks, never double. Order is an immutable record. MatchResult tells you trades, leftover qty, and whether anything rested.

Question to answer: what is the difference between remaining quantity on IOC vs LIMIT?

2

Tree book — the readable matcher

Open book/OrderBook.java then book/PriceLevel.java. Draw two TreeMaps on paper (bids reversed, asks natural).

Trace matchAggressive() with: asks 100×20 and 101×50, then BUY 25 @ 100. You should stop after filling 20 — limit 100 cannot cross 101. Remainder rests if LIMIT.

Then read cancel(): orderIndex finds the level, deque scan removes the order.

./gradlew test --tests 'com.cloblab.engine.MatchingEngineTest'
3

Engine orchestration

Open engine/MatchingEngine.java. All order types share submit():

  1. Match aggressively against the opposite side
  2. If leftover and allowRest (LIMIT only) → addRestingOrder
  3. FOK is special: availableAtOrBetter first, reject with zero trades if not enough

Run the demo and match output to the tests:

./gradlew runDemo
4

Journal + replay

Open journal/OrderEvent.java, EventJournal.java, EventReplayer.java, then the inner class MatchingEngine.Journaled.

Pattern: record the intent (submit/cancel), not the trades. Replay into a fresh engine must rebuild the same book. That is how exchanges recover after a crash.
